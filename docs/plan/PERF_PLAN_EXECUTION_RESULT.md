# 테스트 플랜·실행·실행 목록·결과 화면 속도 개선

작성: 2026-07-31 23:25 KST
대상: testcasecraft v1.0.102
측정 환경: 로컬 (Spring Boot local 프로파일 · PostgreSQL 5434 · macOS arm64)

## 무엇이 느렸는가

측정용 프로젝트를 하나 만들어 규모를 실제 운영에 가깝게 맞췄다 — 케이스 1,200 · 플랜 20 · 실행 40 · **결과 48,000**. 같은 요청을 여섯 번 보내 첫 회(워밍업)를 버리고 중간값을 적었다.

| 화면·요청 | 개선 전 | 개선 후 | 비 |
|---|---:|---:|---:|
| 결과 — 폴더별 통계 (`POST /api/test-results/report`, 미실행 포함 size 2000) | 5.658s | **0.768s** | 7.4배 |
| 결과 — 최신 결과만 50건 (`POST /api/test-results/report`, latestOnly) | 5.391s | **0.288s** | 18.7배 |
| 결과 — 통계 (`GET /api/test-results/statistics`) | 1.096s | **0.160s** | 6.9배 |
| 실행 목록 (`GET /api/test-executions/by-project`, size 50) | 0.174s | 0.189s | — |
| 플랜 목록 (`GET /api/test-plans/project`) | 0.030s | 0.033s | — |
| 첫 화면 JS (프로덕션 빌드) | 6.8MB 한 덩어리 | **733KB** | 9.3배 |

실행·플랜 목록은 원래 빠르던 축이라 이번 측정에서 변화가 드러나지 않는다. 넣은 인덱스는 데이터가 늘 때를 위한 것이다.

## 결과 화면이 5초 걸린 이유

`latestOnly` 나 `includeNotExecuted` 가 켜지면 리포트는 프로젝트의 **모든 결과를 한 번에 메모리로 올린 뒤** 자바에서 최신 결과를 가리고 세고 잘랐다(`PageRequest.of(0, Integer.MAX_VALUE)`). 결과가 48,000건이면 48,000개의 엔티티가 만들어지고, 엔티티마다 태그 컬렉션이 딸려 왔다. 거기에 (플랜:케이스)마다 케이스·플랜을 한 건씩 다시 조회하고, 폴더 경로를 조상까지 거슬러 매번 다시 계산했다. 50건짜리 한 페이지를 보려고 이 일을 전부 했다.

바꾼 방식은 두 단이다.

1. **가릴 때는 컬럼만 읽는다** — 최신 결과·수행 횟수·JIRA 이력을 가리는 데 필요한 여섯 컬럼(`findPopulationRowsByProject`)만 받는다. 엔티티를 만들지 않으므로 태그·첨부·실행자가 딸려오지 않는다.
2. **승자만 엔티티로 읽는다** — 화면에 나갈 (플랜:케이스)별 최신 결과만 `findByIdsWithFetch` 로 다시 읽고, 케이스·플랜 이름과 폴더 경로는 미리 한 번에 적재해 행마다 조회하지 않는다.

통계(`getTestResultStatistics`)도 같은 이유로 느렸다. 실행마다 결과 컬렉션을 지연 로딩해 전부 엔티티로 올린 뒤 자바에서 셌다. 집계에 쓰는 일곱 컬럼만 읽는 조회(`findStatsRowsBy*`)로 바꿨다.

**응답이 같은지 확인한 방법**: 옛 코드로 되돌려(`git stash`) 같은 요청 6종(프로젝트 전체·최신만·플랜 2종·실행 1종·실데이터 프로젝트)의 응답을 받아두고, 새 코드의 응답과 바이트 단위로 비교했다 — 전부 동일. 통계 4종은 `calculatedAt` 타임스탬프만 다르고 수치는 모두 같다. 백엔드 테스트 484건 통과(목 테스트 5건은 옛 조회 메서드를 스텁하고 있어 새 조회로 갱신).

## 첫 화면이 6.8MB였던 이유

`App.jsx` 가 모든 화면을 정적으로 import 해서 번들이 한 덩어리였다. 대시보드만 열어도 차트·PDF·엑셀·마크다운 에디터·스프레드시트까지 받은 뒤에 첫 화면이 그려졌다.

화면 26개를 `React.lazy` 로 바꾸고 `Suspense` 경계 하나를 라우트 위에 뒀다. 첫 요청이 733KB로 줄고, 나머지는 그 화면을 열 때 받는다. `manualChunks` 로 라이브러리를 손수 묶어도 봤지만 엔트리가 특정 갈래를 끌고 오면서 오히려 3MB로 늘어, Vite 기본 분할에 맡겼다(사유는 `vite.config.js` 주석에 남겼다).

브라우저로 다섯 화면(개요·케이스·플랜·실행·결과)을 열어 콘솔 에러 0건, 화면 렌더 확인.

## 그 밖에 손댄 것

- **플랜 목록의 순차 요청** — 플랜마다 자동화 테스트 개수를 물어보는데 `await` 를 줄 세워 플랜 수만큼 왕복이 쌓였다. 한꺼번에 보낸다(`TestPlanList.jsx`).
- **인덱스** — `test_plans` 에는 인덱스가 하나도 없었다(`project_id`, `project_id + created_at` 추가). 실행 목록이 쓰는 `project_id + created_at` 도 없어 함께 넣었다. `ddl-auto: update` 라 재시작 때 생성되며, 로컬에서 생성 확인.

## 남긴 것

- **결과 입력 화면 진입 시 프로젝트 전체 케이스 조회** (`TestCaseResultPage.jsx`, 로컬 755KB) — 이전/다음 케이스 순서를 폴더 계층으로 계산하려고 전체를 받는다. 줄이려면 계층 계산에 필요한 필드만 주는 엔드포인트를 새로 내야 한다. 운영 프로파일은 응답 압축이 켜져 있어(`application-prod.yml:48`) 실제 전송량은 로컬 수치보다 훨씬 작다 — 그래서 우선순위를 낮췄다.
- **`TestResult.tags` 가 EAGER** — 이번에 읽는 엔티티 수를 (플랜:케이스) 개수로 줄여 부담이 사라졌다. LAZY 전환은 트랜잭션 밖 접근에서 깨질 위험이 있어 두었다.
- **실행 상세 표의 가상화 부재** — 케이스가 1,000건을 넘는 플랜에서 스크롤이 무거울 수 있다. 지금은 50건씩 늘려 그리는 방식으로 버틴다.

## 측정 재현

측정용 데이터는 실측 후 지웠다. 다시 만들려면 프로젝트 코드 `PERFBENCH` 로 케이스·플랜·실행·결과를 넣고(48,000건 기준 약 20초), 같은 요청을 6회 보내 중간값을 비교한다.
