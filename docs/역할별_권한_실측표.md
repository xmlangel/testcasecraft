# 역할별 권한 실측표

작성: 2026-08-20 00:10 KST · 대상 브랜치: `feat/project-settings-member-roles`

프로젝트 역할 여섯 종이 사용자 매뉴얼 18-4 규정대로 갈리는지 실행 중인 앱에 요청을 보내 확인한 기록이다. 코드를 읽어 판정한 것이 아니라 응답 코드를 받아 적었다.

## 측정 조건

로컬에서 `SHOW_EXPLORATORY_SESSION_TAB=true ./gradlew bootRun` 으로 띄우고 `http://localhost:8080` 에 요청했다. 데이터베이스는 dev 프로필의 `localhost:5434`, 대상 프로젝트는 ShopFlow(`SHOP`)다.

계정은 실측용으로 새로 만들었다. **시스템 역할은 전부 `TESTER` 로 같게 두고 프로젝트 역할만 달리했다.** 두 역할 축을 섞어 판정하는 결함을 걸러내기 위한 조건이다. 비멤버 계정은 프로젝트에 넣지 않았고, 시스템 ADMIN 은 기존 `admin` 계정을 썼다.

측정을 마친 뒤 계정·세션·차터·업로드 산출물을 모두 지워 원래 상태로 돌렸다.

## 화면 노출 실측

API 응답과 별개로, 화면에 쓰기 버튼이 보이는지 세었다. **DOM 존재가 아니라 실제 표시 여부로 셌다.** 숨긴 요소가 DOM 에 남는 경우가 있어 존재로 세면 통과로 잡힌다.

측정: 2026-08-20 12:30 KST · 실행 상세(`/projects/{id}/executions/{execId}`)

| 계정 | 수정 | 결과 입력 | 결과 보기 | 링크 복사 | 이름 클릭 | 결과 화면 저장 |
|---|---|---|---|---|---|---|
| viewer | 없음 | 0 | 12 | 0 | 결과 화면 | 없음 |
| tester | 없음 | 12 | 0 | 12 | 결과 화면 | 보임 |
| contributor | 보임 | 12 | 0 | 12 | 결과 화면 | 보임 |
| lead · pm · admin | 보임 | 12 | 0 | 12 | 결과 화면 | 보임 |

TESTER 에게 결과 입력만 열리고 기본 정보 수정은 닫힌 것이 매뉴얼 18-4 와 맞는다.

**조회 경로는 역할과 무관하게 열어 둔다.** 결과 기록 권한이 없으면 `입력` 대신 `보기` 가 나오고, 케이스 이름은 누구나 눌러 결과 화면으로 들어간다. 그 화면은 조회 전용 역할에서 저장 버튼 없이 뜬다. 쓰기 입구를 막는 것과 읽을 길을 끊는 것은 다르다. 처음 수정에서 `입력` 을 통째로 감췄더니 조회 전용 사용자가 기록된 결과를 열어 볼 방법이 없어졌다. 결과 입력 링크 복사는 쓰기 흐름이라 그대로 감춘다.

**1.0.113 의 노출 실측에서 이 화면이 빠져 있었다.** 그 회차 기록은 "여덟 화면에서 VIEWER 에게 보이는 쓰기 버튼 0개" 였으나, 실행 상세에서 수정 1개와 결과 입력 12개가 보이고 있었다. 두 가지가 겹쳤다.

- 수정 버튼에 역할 조건이 아예 없었다(`executionId && !isEditingBasicInfo` 만 봄).
- 결과 입력 버튼은 권한이 없을 때 **비활성으로만** 두어 화면에 남았다.

두 번째가 이 저장소에서 반복되는 형태다. 비활성은 "지금은 못 누른다" 를 뜻하고 권한 없음은 "당신에게는 없는 기능" 이라, 같은 표현으로 두면 조회 전용 사용자가 눌러 보고 403 을 받아야 알게 된다. 그래서 **역할 조건과 상태 조건을 나눠** 권한이 없으면 내보내지 않고, 권한은 있으나 실행 상태가 안 맞을 때만 비활성으로 둔다.

## 읽는 법

**VIEWER 는 조회 한 줄만 통과하고 쓰기 열여섯 줄이 모두 403 이다.** 조회 전용 역할의 격리가 성립한다.

**비멤버는 조회조차 못 한다.** 로그인만 한 사용자가 남의 프로젝트 케이스를 덮어쓸 수 있던 경로가 닫혔다.

**TESTER 와 DEVELOPER 가 갈리는 자리가 셋이다.** 케이스 첨부 업로드·케이스 벡터화·플랜 생성에서 TESTER 는 막히고 DEVELOPER 는 통과한다. 결과 기록과 세션 진행은 TESTER 도 통과한다. 매뉴얼 18-4 의 "TESTER 는 조회 + 결과 기록, 탐색 세션 진행" 과 맞는다.

**LEAD 와 PM 이 갈리는 자리는 프로젝트 설정 변경 하나다.** 멤버 관리는 둘 다 되고 설정 변경은 PM 만 된다.

**시스템 ADMIN 만 통과하는 자리는 전체 드래프트 정리다.** 프로젝트를 가리지 않고 전체를 지우는 동작이라 프로젝트 역할로는 열지 않았다.

## 판단이 남은 항목

**TESTER 는 자기가 만든 세션도 지울 수 없다.** 삭제를 리드 이상으로 정한 결과다. 세션은 여러 사람이 함께 보는 기록이라 진행 권한과 삭제 권한을 따로 두었다. 본인이 만든 세션을 지우는 것까지 막을지는 운영 정책으로 정한다. 실측에서 TESTER 가 자기 세션을 지우려 하면 403 이고, 같은 세션을 LEAD 가 지우면 204 다.

**중복 멤버 추가가 500 을 낸다.** 이미 멤버인 사용자를 다시 추가하면 400 이나 409 가 아니라 500 이 나간다. 인가와는 무관하고, 화면에서는 검색 목록이 기존 멤버를 빼 주므로 걸리지 않는다.

## 실측에 쓴 계정

로컬 dev 환경에 남겨 둔 계정이다. 시스템 역할은 `viewer`·`lead`·`pm`·`developer`·`manager`·`tester` 가 모두 `TESTER` 이고, 프로젝트 역할만 다르다. 두 축을 섞어 판정하는 결함을 걸러내려면 이 조건이 필요하다.

| 계정 | 시스템 역할 | ShopFlow·ShopFlow EN 의 프로젝트 역할 |
|---|---|---|
| `admin` | ADMIN | PROJECT_MANAGER |
| `pm` | TESTER | PROJECT_MANAGER |
| `manager` | TESTER | PROJECT_MANAGER |
| `lead` | TESTER | LEAD_DEVELOPER |
| `developer` | TESTER | DEVELOPER |
| `tester` | TESTER | TESTER |
| `contributor` | TESTER | CONTRIBUTOR |
| `viewer` | TESTER | VIEWER |

이 계정은 **ShopFlow 시드가 만든다.** 만드는 곳은 `scripts/shopflow_seed/` 의 `00b_users.py`(등록·비밀번호 교정)와 `02b_members.py`(프로젝트 역할 부여)다. 계정 목록과 비밀번호의 정본은 `scripts/shopflow_seed/i18n.py` 의 `USER_PASSWORDS`·`USER_PROJECT_ROLES` 이고, `07_verify.py` 가 실제 멤버 역할을 그 값과 대조한다. `contributor`(CONTRIBUTOR)까지 더해 프로젝트 역할 여섯 종이 모두 덮인다.

로컬 확인용이므로 배포 환경에는 만들지 않는다.
