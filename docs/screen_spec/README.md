## 1. 이 문서 묶음이 무엇인가

TestcaseCraft의 **실제 화면을 화면 단위로 분해한 기획 문서**다. 화면마다 네 개의 문서를 두고, 업무 흐름 → 화면 구성 → 구성요소 규격 → 요건 추적의 순서로 좁혀 간다.

사용자 매뉴얼(`../manual/new/USER_MANUAL.md`)과 역할이 다르다. 매뉴얼은 "어떻게 쓰는가"를 사용자에게 설명하고, 이 문서는 "무엇이 왜 그렇게 되어 있는가"를 기획·인수 관점에서 기술한다. 같은 화면을 다루더라도 매뉴얼은 절차, 이 문서는 영역·요소·상태·권한·규칙을 다룬다.

### 서술의 기준

**기준은 화면이다.** 지금 돌아가는 화면을 보고 쓰므로 "이렇게 되어 있다"로 기술한다. 소스 코드의 파일 이름이나 행 번호는 적지 않는다. 기획 관점에서 필요한 것은 "화면이 무엇을 보여주고 어떻게 반응하는가"이고, 구현 위치는 코드를 고치면 바뀌는 값이다.

화면만 보고 판정이 갈리는 지점은 `⚠ 확인 필요`로 표시하고 무엇을 확인해야 하는지 함께 적는다. 예시 데이터는 캡처에 쓰인 데모 프로젝트(ShopFlow · ShopFlow EN)를 그대로 쓴다.

## 3. 화면 폴더의 4문서 구조

| 파일 | 무엇을 답하는가 | 주 독자 |
|---|---|---|
| `01_<화면>_업무프로세스.md` | 이 화면이 어떤 업무를 맡고, 전후 화면과 어떻게 이어지며, 누가 무엇을 할 수 있는가 | 기획 · QA 리드 |
| `02_<화면>_화면정의.md` | 화면을 영역 A~n으로 나눈 배치, 영역별 요소 · 표시 규칙 · 상태 · 권한별 차이 | 기획 · 설계 · 개발 |
| `03_<화면>_컴포넌트.md` | 구성요소 규격, 표시·상호작용 규칙, 상태 전이, 설정 저장 위치 | 설계 · 개발 |
| `04_요건반영목록.md` | 요건 ↔ 화면 영역 추적표, 정정 대상, 확인 필요 항목 | 인수 검토 · 유지보수 |
| `images/*.svg` | 화면 배치도 | 전원 |

한 화면의 네 문서는 서로를 가리킨다. **02에 있는 영역·요소는 04에 행이 있어야 하고, 04에만 생긴 요소는 02·03에 되돌려 적는다.**

## 4. 표기 규약

### 참조 표기

| 표기 | 뜻 |
|---|---|
| `/projects/{projectId}/testcases` | 화면 라우트 |
| 매뉴얼 4-4절 | `../manual/new/USER_MANUAL.md`의 절 번호 |
| 02 영역 C | 같은 화면 폴더 02 문서의 영역 |
| 01 5.2절 | 같은 화면 폴더 01 문서의 절. `§` 기호는 쓰지 않는다 |
| S4 → S6 | 화면 사이 이동 |
| `⚠ 확인 필요` | 화면만 보고는 판정이 갈려 실행 확인이 필요한 지점 |

### 권한 표기

프로젝트 권한 6종과 시스템 권한을 함께 쓴다. 판정 규칙은 `00_전체_업무프로세스.md` 5절.

`RW` 조회+편집 · `R` 조회만 · `W(결과)` 결과 기록만 · `—` 접근 불가

### 상태 표기

| 표기 | 뜻 |
|---|---|
| 정상 | 요건이 화면에 구현되어 동작한다 |
| **부분** | 일부 조건에서만 동작한다. 어떤 조건인지 함께 적는다 |
| **숨김** | 기능은 있으나 화면에 진입점이 없다. 사유와 해제 조건을 적는다 |
| **환경 의존** | 환경 설정·외부 서비스 상태에 따라 노출이 갈린다 |

### 문체

한다체(`~한다` · `~이다` · `~않는다`)로 쓴다. 화면에 실제로 뜨는 문구를 인용할 때만 원문을 그대로 옮긴다.

## 5. HTML 뷰어 — 문서와 실제 화면을 오가며 본다

`index.html` 을 브라우저로 열면 화면 12개를 눌러 가며 배치도와 4문서를 본다. 외부 리소스를 쓰지 않으므로 파일을 그대로 열거나 그대로 보내도 된다.

| 하는 일 | 방법 |
|---|---|
| 화면 고르기 | 왼쪽 목록. `문서 안내` 화면에는 화면 지도 카드가 함께 나온다 |
| 문서 보기 | 상단 탭 — 업무프로세스 / 화면정의 / 컴포넌트 / 요건반영목록 |
| **기획과 현재 화면 대조** | `배치도` · `실제 화면` · `나란히` 탭. 나란히는 왼쪽에 기획 배치도, 오른쪽에 매뉴얼 캡처를 놓는다 |
| 캡처 크게 보기 | 캡처를 누르면 화면 전체로 펼친다. `Esc` 나 배경 클릭으로 닫는다 |
| **실제 화면 열기** | 상단에 앱 주소와 프로젝트 ID를 한 번 넣으면 라우트 칩이 링크가 된다. 눌러서 새 탭으로 그 화면을 연다 |
| 문서 가로질러 찾기 | 상단 검색창. 결과를 누르면 그 문서로 이동한다 |

앱 주소와 프로젝트 ID는 브라우저에 남으므로 다시 넣지 않아도 된다.

**실제 화면 캡처는 매뉴얼의 것을 쓴다.** 각 화면 02 문서 머리말의 캡처 목록이 무엇을 보여줄지 정하므로, 캡처를 늘리려면 매뉴얼에 먼저 추가한 뒤 그 목록에 파일 이름을 적는다.

문서나 캡처를 고친 뒤에는 다시 만든다.

```
python3 docs/screen_spec/build_html.py            # 캡처는 매뉴얼 폴더를 상대 경로로 참조 (1.5 MB)
python3 docs/screen_spec/build_html.py --embed    # 캡처까지 심는다 (8.7 MB, 파일 하나로 공유)
```

저장소에 두는 것은 상대 경로 판이다. 저장소 없이 파일 하나만 보낼 때 `--embed` 로 다시 만든다.

## 6. 화면에서 문서를 찾는 방법

앱의 **오른쪽 아래에 화면 ID가 작게 뜬다.** 지금 보고 있는 화면이 어느 문서에 해당하는지 바로 알 수 있다. 마우스를 올리면 화면 이름이 함께 나오고, 이름은 사용자의 언어 설정을 따른다.

| 배지 | 문서 |
|---|---|
| `S4` | `docs/screen_spec/4.테스트케이스/` |
| `S6` | `docs/screen_spec/6.테스트실행/` |

주소로 화면 ID를 판별하는 규칙은 `src/main/frontend/src/constants/screenIds.js` 한 곳에 있다. **화면을 새로 만들거나 주소를 바꾸면 그 규칙과 이 문서의 화면 목록을 함께 고친다.** 한쪽만 고치면 배지가 엉뚱한 문서를 가리킨다.

규칙에 없는 주소에서는 배지를 그리지 않는다. 틀린 ID를 보여주는 것보다 안 보이는 편이 낫다.

## 7. 갱신 규칙

1. **화면을 바꾸면 그 화면의 4문서를 함께 고친다.** 영역이 늘면 02·03·04 세 곳에 행이 생긴다.
2. **라우트를 바꾸면 `00_전체_업무프로세스.md` 6절 라우트 표가 정본이다.** 화면별 문서는 그 표를 참조만 한다.
3. **권한 판정을 바꾸면 `00_전체_업무프로세스.md` 5절을 먼저 고친 뒤** 각 화면의 권한표를 맞춘다. 권한표가 네 곳에 흩어지면 드리프트가 시작된다.
4. **배치도는 SVG로 둔다.** ASCII 도해를 새로 만들지 않는다. 화면 배치가 바뀌면 해당 폴더 `images/` 의 SVG를 고친다.
5. **캡처는 이 문서에 새로 만들지 않는다.** 매뉴얼의 `images/`·`images_en/`을 참조하고, 부족하면 매뉴얼 쪽에 추가한 뒤 여기서 가리킨다.
6. 머리말의 기준 버전을 갱신한다.
7. **문서를 고친 뒤 검증 루틴을 돌린다.**

```
python3 docs/screen_spec/validate.py
```

구조·제목·머리말 규격, 라우트와 요건 ID 일관성, 표와 코드블록 무결성, 상호참조 링크, 캡처 파일 존재, 배치도 SVG의 겹침·이탈, 금지 항목(소스 파일명·행 번호·테스트 식별자·내부 식별자)을 한 번에 검사한다. 어긋난 곳이 있으면 종료 코드 1을 돌려주므로 CI에 걸어도 된다.

화면에 실제로 뜨는 안내 문구를 인용한 자리는 합니다체가 남는다. 검증은 이것을 오류가 아니라 확인 권고로 알린다.
