## 1. 이 문서 묶음이 무엇인가

TestcaseCraft의 **실제 화면을 화면 단위로 분해한 기획 문서**다. 화면마다 네 개의 문서를 두고, 업무 흐름 → 화면 구성 → 구성요소 규격 → 요건 추적의 순서로 좁혀 간다.

사용자 매뉴얼(`../manual/new/USER_MANUAL.md`)과 역할이 다르다. 매뉴얼은 "어떻게 쓰는가"를 사용자에게 설명하고, 이 문서는 "무엇이 왜 그렇게 되어 있는가"를 기획·인수 관점에서 기술한다. 같은 화면을 다루더라도 매뉴얼은 절차, 이 문서는 영역·요소·상태·권한·규칙을 다룬다.

### 목업 문서와 다른 점

이 문서 묶음의 형식은 `온토비아1.1-목업`의 4문서 구조를 가져왔다. 그쪽은 아직 만들지 않은 화면의 제안서라서 `(개발 중)`·`(가정)` 배지와 미결 항목 표가 문서의 중심이었다.

TestcaseCraft는 이미 돌아가는 제품이다. 그래서 다음을 바꿨다.

| 항목 | 목업 문서 | 이 문서 |
|---|---|---|
| 서술의 시제 | "이렇게 만들 것이다" | "이렇게 되어 있다" |
| 미구현 표기 | `(개발 중)` 배지 | 실제로 숨겨진 기능만 사유와 함께 기록 |
| 권한 | 목업용 제안 매트릭스 | 화면에서 확인한 역할 6종의 실제 판정 |
| 예시 데이터 | 가상 3건 | 캡처에 쓰인 데모 프로젝트(ShopFlow · ShopFlow EN) |
| 검증 방법 | PM 확정 대기 | 화면을 열어 대조 |

**서술의 기준은 화면이다.** 소스 코드의 파일 이름이나 행 번호는 적지 않는다. 기획 관점에서 필요한 것은 "화면이 무엇을 보여주고 어떻게 반응하는가"이고, 구현 위치는 코드를 열면 바뀌는 값이다. 화면만 보고 판정이 갈리는 지점은 `⚠ 확인 필요`로 표시하고 무엇을 확인해야 하는지 함께 적는다.

## 3. 화면 폴더의 4문서 구조

| 파일 | 무엇을 답하는가 | 주 독자 |
|---|---|---|
| `01_<화면>_업무프로세스.md` | 이 화면이 어떤 업무를 맡고, 전후 화면과 어떻게 이어지며, 누가 무엇을 할 수 있는가 | 기획 · QA 리드 |
| `02_<화면>_화면정의.md` | 화면을 영역 A~n으로 나눈 배치, 영역별 요소 · 표시 규칙 · 상태 · 권한별 차이 | 기획 · 설계 · 개발 |
| `03_<화면>_컴포넌트.md` | 구성요소 규격, 표시·상호작용 규칙, 상태 전이, 설정 저장 위치 | 설계 · 개발 |
| `04_요건반영목록.md` | 요건 ↔ 화면 영역 추적표, 정정 대상, 확인 필요 항목 | 인수 검토 · 유지보수 |
| `images/*.svg` | 화면 배치도 | 전원 |

한 화면의 네 문서는 서로를 가리킨다. **02에 있는 영역·요소는 04에 행이 있어야 하고, 04에만 생긴 요소는 02·03에 되돌려 적는다.**

## 4. 표기 규약

### 참조 표기

| 표기 | 뜻 |
|---|---|
| `/projects/{projectId}/testcases` | 화면 라우트 |
| 매뉴얼 4-4절 | `../manual/new/USER_MANUAL.md`의 절 번호 |
| 02 영역 C | 같은 화면 폴더 02 문서의 영역 |
| 01 5.2절 | 같은 화면 폴더 01 문서의 절. `§` 기호는 쓰지 않는다 |
| S4 → S6 | 화면 사이 이동 |
| `⚠ 확인 필요` | 화면만 보고는 판정이 갈려 실행 확인이 필요한 지점 |

### 권한 표기

프로젝트 권한 6종과 시스템 권한을 함께 쓴다. 판정 규칙은 `00_전체_업무프로세스.md` 5절.

`RW` 조회+편집 · `R` 조회만 · `W(결과)` 결과 기록만 · `—` 접근 불가

### 상태 표기

| 표기 | 뜻 |
|---|---|
| 정상 | 요건이 화면에 구현되어 동작한다 |
| **부분** | 일부 조건에서만 동작한다. 어떤 조건인지 함께 적는다 |
| **숨김** | 기능은 있으나 화면에 진입점이 없다. 사유와 해제 조건을 적는다 |
| **환경 의존** | 환경 설정·외부 서비스 상태에 따라 노출이 갈린다 |

### 문체

한다체(`~한다` · `~이다` · `~않는다`)로 쓴다. 화면에 실제로 뜨는 문구를 인용할 때만 원문을 그대로 옮긴다.

## 5. 갱신 규칙

1. **화면을 바꾸면 그 화면의 4문서를 함께 고친다.** 영역이 늘면 02·03·04 세 곳에 행이 생긴다.
2. **라우트를 바꾸면 `00_전체_업무프로세스.md` 6절 라우트 표가 정본이다.** 화면별 문서는 그 표를 참조만 한다.
3. **권한 판정을 바꾸면 `00_전체_업무프로세스.md` 5절을 먼저 고친 뒤** 각 화면의 권한표를 맞춘다. 권한표가 네 곳에 흩어지면 드리프트가 시작된다.
4. **배치도는 SVG로 둔다.** ASCII 도해를 새로 만들지 않는다. 화면 배치가 바뀌면 해당 폴더 `images/` 의 SVG를 고친다.
5. **캡처는 이 문서에 새로 만들지 않는다.** 매뉴얼의 `images/`·`images_en/`을 참조하고, 부족하면 매뉴얼 쪽에 추가한 뒤 여기서 가리킨다.
6. 머리말의 기준 버전을 갱신한다.
